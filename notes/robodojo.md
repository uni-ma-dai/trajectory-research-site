# RoboDojo 评测：五类能力、成功标准与轨迹评分

讨论稿 · 2026-10-13 · 依据当前本地源码。与 [XPolicyLab wrapper 与重复 rollout](xpolicylab.md) 配套阅读。

目标：理解评测分数到底衡量什么，并设计“同一 datagen 场景重复 rollout”的轨迹对照。本文没有启动新评测，也没有改变此前暂停后续任务的安排。

## 1. 先回答：是不是比较稀疏？

是，当前机制主要是**离散条件触发的成功判定和阶段得分**。部分任务能给中间进度分，但不是每一步按距离连续变好的 dense reward。

需要区分三件事：

| 名称 | 代码含义 | 能否区分轨迹细节 |
| --- | --- | --- |
| success | 是否满足任务成功条件 | 只能区分成败 |
| process/final score | 达成哪些离散条件或阶段 | 能区分部分进度 |
| 轨迹质量指标 | 路径长度、耗时、平滑性、误差、行为差异等 | 需要额外记录与分析 |

两条轨迹可以同为 100 分，但一条绕路、另一条直接完成；两条也可以同为 0 分，但一条接近成功，另一条没有抓起物体。因此任务分数适合作为结果标签，不能独自承担轨迹差异分析。

## 2. 五类是能力分类，不是五套评分公式

官方核心分类如下；网站现在另外列有 DLC 附加入口，不应误认为核心能力从五类变成六种评分机制。分类来源：[官方仿真任务目录](https://robodojo-benchmark.com/doc/sim-tasks/)。具体阈值以下均按本地任务代码解释。

| 能力类别 | 主要考察什么 | 本文代表任务 |
| --- | --- | --- |
| Generalization（泛化） | 物体、布局及随机变体变化下的操作 | `stack_blocks` |
| Memory（记忆） | 顺序、遮挡前信息和历史状态 | `cover_blocks` |
| Precision（精确操作） | 插入、对齐等空间精度 | `insert_tubes` |
| Long-Horizon（长时序） | 连续完成多个子目标 | `fill_egg_holder` |
| Open（开放条件任务） | 语言、图像或语义条件下的目标选择 | `solve_equation` |

分类说明任务设计意图，评分仍由每个任务实现。某个阶段分数不能单独证明模型具备对应认知能力；例如记忆类任务仍通过实际行为序列来判分。

## 3. 评分调用链：先注册规则，再执行检查

```text
eval_env.run_eval()
  → task.run_reward()        注册成功条件
  → task.get_score()         若存在，注册阶段/末态评分条件
  → eval_one_episode()      策略闭环执行
      → take_action_batch()
      → 仿真执行当前 action
      → reward_manager.step()
      → is_episode_end() / get_reward()
  → 根据成功标记和部分得分结算
  → 写入 _result.json
```

特别容易误解的是：任务里的 `get_score()` 通常是在注册评分表；`reward_manager.get_score()` 才读取已经积累的分数。名字相同，职责不同。

规则最终由 `func_parser.py`（源码路径；公开版见代码摘录页） 从仿真真值检查，包括包围盒、功能点、位置距离、轴向关系、关节位置、夹爪和机械臂归位。不是根据视频用人工或视觉模型打分。

评分检查位于高层 action 执行后的调用链，不能假设每个物理子步都记录了一次阶段分数。任务 `step_lim` 限制的是 `take_action_cnt`，也不是直接限制视频帧数或物理步数。

## 4. RewardManager 的规则语义

| 注册接口/模式 | 语义 |
| --- | --- |
| `check` | 成功条件队列，每次检查当前首组，通过后弹出，能表达先后顺序 |
| `final_check` | 在启用 final check 的结算检查中验证末态 |
| `query` / trigger 系列 | 计数、禁止事件、条件触发或边沿事件 |
| `score(..., paired)` | 独立条目达成后累加对应分值 |
| `score(..., by_count)` | 根据已完成条目数量查分值表；不是把分值表相加 |
| `score(..., transition)` | 只检查下一阶段，每次 step 最多前进一阶段；返回当前阶段的分数 |
| `final_score` | 注册结算阶段的评分条目，过程分与末态分可合并 |

阶段内外层检查通常要求全部通过，但嵌套列表不是一律 AND：`check_once()` 默认将列表解释为 OR，更深嵌套再交替为 AND。因此读任务时必须连同列表层级一起看。

过程分达成后通常被记住，物体后来掉落不一定撤销此前的全部分数；完整任务成功还需单独判断。另有满分门控：当完整任务尚未成功时，`transition/by_count` 当前档位恰为 100 会回退到前一档；`paired` 已得分之和恰为 100 时会扣掉最后获得的那项。不能把代码概括成“失败统一扣固定分”，也不能推广为自动将任意分值裁剪到 99。

## 5. 每类看一个具体例子

### 5.1 泛化：stack_blocks

源码：`stack_blocks.py`（源码路径；公开版见代码摘录页）。这是 RoboDojo 的三个方块任务，与 RoboTwin 的 `stack_blocks_two` 不同。

- 成功：三个方块满足 `is_stacked`，且机器人归位。
- 阶段分：`[15, 100]`，`transition`。
- 第一阶段：任意一对方块堆叠且夹爪打开；第二阶段：三个堆叠且夹爪打开。
- XY 阈值按资产索引选择 0.015、0.0175 或 0.02 m，默认 0.015 m；`is_stacked` 还包含其他几何判定，不能只看 XY 距离。
- 三个已经堆好但未满足完整归位条件，不意味着最终就有 100 分。

轨迹研究：比较抓取顺序、失败位置和放置偏差；同时区分改变物体/布局带来的泛化差异与同一场景的采样差异。

### 5.2 记忆：cover_blocks

源码：`cover_blocks.py`（源码路径；公开版见代码摘录页）。

- 按初始位置确定左、中、右方块，要求按序覆盖；随后按颜色次序揭开。
- 评分阶段为 `[0, 0, 5, 15, 30, 100]`，`transition`：覆盖左、覆盖左中、全部覆盖、揭开红、再揭开绿、全部揭开。
- 杯子倒扣轴向要求阈值为 10°；完整成功还包含机器人归位。
- `query` 要求红绿蓝方块移动超过 0.05 m 的事件次数为 0。

前两个阶段虽然推进了状态，分数仍然是 0。这是“有行为进展但分数不变”的具体例子。研究时应记录阶段索引和事件，而不只记录分数；模型 reset 也必须清除上一次 trial 的历史状态。

### 5.3 精确操作：insert_tubes

源码：`insert_tubes.py`（源码路径；公开版见代码摘录页）。

- 每根管子同时满足：在槽内、深度条件、局部 y 轴朝上（30°阈值）。
- 深度判据实际为 `B_z_max - A_z_min > 0.045`，来自包围盒世界 z 范围；不能只凭函数名当作精确测量的真实插入行程。
- 阶段分 `[20, 40, 100]`，分别对应完成一、二、三根，评分还要求夹爪打开。
- 完整成功要求三根均通过，以及机器人归位。

轨迹研究：记录孔口接近、横向误差、姿态偏差、插入深度等连续量，才能解释“差一点插入”和“完全没对准”的差异。

### 5.4 长时序：fill_egg_holder

源码：`fill_egg_holder.py`（源码路径；公开版见代码摘录页）。

- 分别检查四个物体位于蛋盒中，并满足相对盒底的高度范围。
- 阶段分 `[10, 25, 40, 90]`，逐个反映已放好一至四个物体，采用 `transition`。
- 完整成功还检查蛋盒关节比例达到 0.9 对应条件，以及机器人归位。
- 四个都放好可到 90；完整任务成功由评测器直接记为 100。

这些分值是阶段总分：第二阶段 25，不是 10+25。研究时重点分析在哪个子目标首次分叉、此前成功子目标是否被后来动作破坏，以及完整任务耗时。

### 5.5 Open：solve_equation

源码：`solve_equation.py`（源码路径；公开版见代码摘录页）。

- 根据场景已有数字/运算符算出可接受的缺失项，选择正确候选放到缺失垫上。
- XY 位置阈值 0.018 m，两个轴分别要求与世界 x/y 方向在 45°阈值内，并要求机器人归位。
- 此任务文件没有定义阶段 `get_score()`；当前这条评测路径主要是成功 100、失败 0。

轨迹研究应拆分“选对物体了吗”和“操作完成了吗”。总分为 0 可能是语义选错，也可能是正确物体没有放准。

这些例子只代表对应任务的实现，不代表同一能力类别内所有任务共享这张评分表。选择新任务时按相同方法阅读它的 `run_reward()`、`get_score()` 与谓词实现。

## 6. 结果文件的分母和单位

在 `eval_env.py`（源码路径；公开版见代码摘录页） 的 `run_eval()` 中，对有效 episode：

```text
episode_score = 1                         如果任务成功
              = process_score / 100       如果失败且任务提供阶段评分
              = 0                        否则

success_rate = 成功 episode 数 / 有效 episode 数
score        = 100 × episode_score 的平均值
```

`details` 每条保存 `layout_id`、`success`、`score`，其中单条 score 是通常 0–1 的量；顶层 score 是通常 0–100 的量。顶层 success_rate 是 0–1。success_rate 和 score 不要混用。

不稳定场景在当前本地评测逻辑中单独计数，排除出有效评测样本；PhysX 损坏等情况还可能触发放弃 layout 和补位。报告应同时列 attempted、valid、success、fail、unstable/abandoned，不能只保留最后分数。

本文件中的公式是单次任务评测的聚合。五类之间如何汇总应另行声明，不从这里推断官方榜单权重。自己的研究可同时报告每个场景的 K 次均值、任务均值和类别宏平均，避免样本多的任务支配总分。

## 7. 固定 datagen 场景，重复 rollout 的设计

标准评测已有保存布局回放入口：`SeedManager.init_eval()` 从 `assets/Eval_Layout/<benchmark>/<config>/<eval_seed>/` 读取任务 JSON，排序后分配 layout_id；reset 时经 `set_saved_layout()` 重建。

因此目前的 `--seed` 不应直接理解成“本次模型采样随机种子”：它参与选择布局目录。layout_id 是排序后的索引，也不应假设永远等于文件名数字。用于研究时记录路径和内容哈希。

如果 datagen 输出场景来自另一个格式或 RoboTwin，不能直接宣称可被 RoboDojo 加载。先确认它能转换为 RoboDojo layout schema，并验证资产、初始关节、物体位姿与任务元信息。保存布局也不是完整物理引擎快照，重建后需要检查实际初始状态和稳定性。

建议实验分两步：

1. 重复性基线：一个简单刚体场景、一个模型、同一策略 RNG 初态，重复 3 次，测物理/数值噪声底线。
2. 多样性实验：固定相同场景、模型、指令、执行时序，只改变策略采样随机性，重复 K 次（先 K=5）。

在不同模型间比较时，再固定同一组场景和执行预算。首轮使用单环境和独立 policy 状态，避免共享 RNG 与批次顺序混入结果。

标准续跑会按 completed_layout_ids 去重；直接重复同一 layout_id 可能被过滤。需要增加 `(scene_id, repeat_id, policy_id, policy_seed)` 身份和独立结果目录，或为每次 trial 使用独立运行目录及明确的 layout 选择入口。仅重复同一条原评测命令不是可靠的重复实验接口。

## 8. 为了比较轨迹，还需要记录什么？

当前 `_result.json` 和流式视频不足以数值重建完整轨迹。建议增加独立 recorder，不修改官方评分定义：

| 记录 | 用途 |
| --- | --- |
| 场景 JSON 哈希、资产/配置版本、初始状态 | 证明比较的是同一场景 |
| 模型 checkpoint、归一化统计、精确指令、策略 seed | 控制模型条件 |
| step、仿真时间、chunk_id、chunk 内索引 | 区分控制步、物理时间和推理次数 |
| 模型原始 action、适配后 action、实际 qpos/末端位姿 | 区分模型差异、适配差异与跟踪误差 |
| 目标物体位姿、夹爪、任务阶段和每条谓词结果 | 定位失败与行为分叉 |
| score、success、结束原因、异常/不稳定标记 | 与任务评测保持关联 |

建议分析：

- 任务结果：成功率、部分得分分布、首次失败阶段。
- 几何：末端路径长度、物体路径、抓取/放置位置偏差、按阶段或 DTW 对齐后的轨迹距离。
- 时间：仿真完成时长、阶段时长、推理延迟；墙钟耗时另列。
- 控制：速度/加速度及跟踪误差，需要真实时间戳和实际状态，不能仅差分压缩视频帧。
- 行为：用哪只手、先抓哪个物体、重试次数、是否绕行；成功轨迹和失败轨迹分别分析。

不要直接把两条不同长度轨迹按帧相减。先明确比较的是同一物理时间、相同任务阶段还是归一化进度。额外的密集距离指标属于研究诊断，不能冒充官方任务分数。

## 随机性链路补充（2026-10-14）

场景由 benchmark 环境管理；XPolicyLab 适配模型输入输出和推理。当前 RoboDojo 评测是读取保存布局：`SeedManager.init_eval → get_seed_scene_info → set_saved_layout → reset → load_saved_layout / apply_saved_poses → 稳定性检查与机器人初始化`。`eval_seed` 选目录，`layout_id` 是排序后文件列表的枚举索引；该索引也传入环境 reset 的 seed 链路。新增或移除文件可能改变索引对应关系，建议另存实际文件路径和哈希。

不能据此称 RoboDojo 完全没有随机性：布局管理器仍有背景、房间、桌面和灯光选择分支。评测明确设置 replay；背景优先读取保存值。房间/桌面的 random 标志、灯光 types 列表若仍留在输入配置中，相应选择分支仍可能采样。当前核实的是评测恢复链路，未定位到本 checkout 中完整的 datagen 布局采样保存入口，不把这些辅助函数拼成一条已证实的 datagen 链。

布局恢复后还有物理 settling，因此 JSON 相同不等于完整仿真快照相同；要比较同场景，应记录 reset 完成后的实际初态、指令和观测。仿真误差是否导致当前 rollout 分叉尚未测量。

现有 `trial_id` 是任务名与运行 ID 构成的 ModelClient 通信标识，不是重复序号。`repeat_id`、`layout_hash`、显式接入 RNG 的 `policy_seed` 和统一 `policy_id` 是后续实验建议，不是已实现参数。


### 首轮 policy_seed 实验实现

新增独立入口 `scripts/run_seeded_dojo_trial.py`：固定 stack_blocks 布局 0、Pi_05 checkpoint 59999，独立结果目录运行四次 `[0,0,1,2]`。脚本记录 layout_hash、repeat_id、模型服务 seed 确认值、初始观测和每步动作/实际状态；不会改写标准评测的布局去重规则。模型 RNG 控制由 Pi_05 新增公开接口完成，限独立服务单环境串行使用。

原始记录在 `[data]/outputs/rollout_variation/dojo-pi05-seeds/`；`scripts/summarize_seed_rollouts.py` 将紧凑实测摘要同步到网页。运行结果以摘要实际状态为准，不把未完成或异常退出计为任务失败。

### 首轮实测结果（2026-10-14）

| repeat_id | policy_seed | 动作步数 | success | 最终分 / 100 | 首次阶段分 |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 | 550 | false | 0 | 无 |
| 1 | 0 | 550 | false | 15 | 第 267 步得到 15 分 |
| 2 | 1 | 550 | false | 0 | 无 |
| 3 | 2 | 550 | false | 0 | 无 |

四次布局哈希一致，记录到的初始物体位姿和机械臂关节状态逐值相同。初始观测差异位于三路相机图像；第二次 seed=0 对比第一次，像素通道平均绝对差约 0.295–0.378（uint8 0–255），但第一步目标动作就出现差异。因此当前闭环对照含观测差异，不能将分叉全部归因于策略 seed，也未证明是 PhysX 误差导致。

另用同一份初始观测做严格的离线推理对照：两次 seed=0 的整个动作 chunk 完全一致；seed=1、2 对比 seed=0 的最大绝对动作差分别约 0.04990、0.58734（各维原单位）。这证明当前 JAX 策略 RNG 接口生效，不代表不同 seed 的性能优劣。

相对首次 rollout，另外三次在共同 550 个动作步上的实际机械臂关节 RMSE 分别约 0.59270、0.46650、0.65737；这是按动作步直接对齐的差异指标，不是质量分。网页还展示同一方块的实际 XY 运动投影。仅一个场景、四次 rollout，不能用于估计总体成功率。
